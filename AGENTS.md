# Campus: правила роботи агента

## Контекст

- Flask + SQLAlchemy/pg8000, PostgreSQL, HTML/CSS/JavaScript. Інтерфейс українською.
- Поточна локальна база: Docker `postgres-dev`, `127.0.0.1:5432`, база `campus`, роль `campus_app`.
- `scripts/local_db.py` — окремий альтернативний кластер на `55432`; не підміняй ним Docker-конфігурацію.
- Перед роботою перевір актуальні файли й Git-статус. Зберігай зміни користувача.

## Секрети та персональні дані

- Не друкуй `.env`, паролі, токени, приватні ключі, SQL з паролями чи необроблений `docker inspect`.
- Діагностика має показувати лише дозволені поля. Винятки й зовнішній вивід перевіряй на секрети перед відображенням.
- Передавай секрети через захищене введення або пам’ять процесу, не через командний рядок чи журнали.
- У прикладах використовуй лише очевидні заповнювачі. Реальні записи студентів не додавай до коду, тестів, документації чи архівів.
- `.env`, `.local/`, `.venv/`, дампи й журнали мають залишатися поза Git та ZIP.

## Межі повноважень

- Без підтвердження користувача не змінюй паролі, ролі/права доступу, мережеву доступність, налаштування автентифікації чи схему робочої БД.
- Не видаляй бази, наявні дані, контейнери чи volumes; не запускай `docker compose down -v`, `docker volume rm`, `git reset --hard`, `git clean` або переписування історії без явного погодження конкретної дії.
- Не виконуй push, публікацію, створення віддаленого репозиторію чи завантаження артефактів без явної вказівки користувача.
- Згода, вже надана в поточному обговоренні на конкретну дію, достатня; не запитуй її повторно без зміни обсягу.
- Для міграцій спочатку покажи зміни та план резервування/відновлення. `db current`, `db heads`, `db check` дозволені для діагностики.

## Перевірки

- Використовуй Python із `.venv`, не змінюй глобальні пакети.
- Швидкі тести: `./.venv/Scripts/python.exe -m pytest -q`.
- PostgreSQL: `./.venv/Scripts/python.exe -m pytest -q --postgres`. Вони створюють випадкові схеми `test_<uuid>` і видаляють лише власні тестові схеми. Виконуй на погодженій локальній/тестовій БД; запит користувача запустити тести дозволяє цей тестовий цикл.
- Не спрямовуй тести на production. Не видаляй сторонні схеми за префіксом `test_`.
- Для HTTP-перевірок використовуй унікальні синтетичні записи й прибирай лише створені цією перевіркою ID.
- Перевір секрети: `./.venv/Scripts/python.exe scripts/check_secrets.py`.
- Перевір міграції: `./.venv/Scripts/python.exe -m flask --app run db current` та `db check`. Не запускай `db upgrade` як приховану частину аудиту.
- Перед передачею коду перевір `.gitignore`, список відстежуваних файлів (якщо Git ініціалізований), секрети та склад ZIP.

## Пакування і звітність

- ZIP створюй лише через `scripts/package-source.ps1`; список дозволених файлів — `source-manifest.json`.
- Не додавай нові файли до маніфесту автоматично: перевір призначення та вміст кожного.
- Не вимикай перевірки шляхів, символічних посилань чи секретів задля успішного пакування.
- Звіт має розрізняти виконані зміни, рекомендації, результати тестів і межі перевірки.
- Публікація вихідного коду не означає готовність застосунку до публічного доступу: зараз авторизації немає.
