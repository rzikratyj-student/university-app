# Campus: аудит безпеки та підготовка до GitHub

Дата: 2026-10-12. Обсяг: локальні вихідні файли, правила Git, ZIP, Flask,
контейнер `postgres-dev`, PostgreSQL та перевірки застосунку.
Паролі, їхні хеші й дані студентів у цьому звіті не наведено.

## Висновок

Вихідний код можна готувати до GitHub за наведеними нижче перевірками.
Застосунок залишається локальним навчальним інструментом: без авторизації
він не готовий до публічного доступу з реальними даними студентів.
Це перевірка конфігурації та коду, а не повний пентест чи перевірка всіх CVE залежностей.

## Git та секрети

- Коренева папка не є Git-репозиторієм: `.git` відсутня, `git status` і
  `git ls-files` це підтвердили. Немає локального індексу/історії для аналізу;
  це не доводить відсутність попередніх зовнішніх публікацій.
- Початковий `.gitignore` вже виключав `.env`, `.local/`, `.venv/`, `instance/`
  та основні Python-кеші. Додано варіанти `.env.*` із винятком `.env.example`,
  SQLite/DB-файли, дампи, резервні копії, журнали, архіви, додаткові кеші,
  каталоги PostgreSQL та приватні ключі.
- Правила `.gitignore` не захищають уже відстежувані файли й можуть бути
  обійдені `git add -f`. Після ініціалізації обов’язково перевірити індекс.
- Перевірено вихідний код, тести, міграції, README та `.env.example` на збіги
  з фактичними локальними паролями, включно з паролем адміністратора Docker:
  збігів не знайдено. Заповнювачі в прикладах не є чинними обліковими даними.
- Додано `scripts/check_secrets.py`: евристики приватних ключів, поширених
  токенів, літеральних секретів та URL з паролями. Значення не друкуються.
  Сканер не гарантує виявлення всіх форматів секретів і не сканує історію Git.
- Чинні секрети залишаються локально в `.env`, `.local/db-password` та
  метаданих контейнера; ці джерела не включені до архіву.

## Docker та PostgreSQL: фактичний стан

| Перевірка | Результат та значення |
|---|---|
| Образ | `postgres:18`; тег змінний, оновлення слід перевіряти й фіксувати digest |
| Опублікований порт | `127.0.0.1:5432`, не всі зовнішні інтерфейси хоста |
| Мережа | Docker `bridge`; PostgreSQL усередині слухає `*`, доступ можливий також з дозволених контейнерних мереж |
| Privileged | Вимкнено |
| Restart policy | `unless-stopped` |
| Збереження даних | Volume `postgres_data` → `/var/lib/postgresql`; PGDATA `/var/lib/postgresql/18/docker` |
| Пароль адміністратора | Заданий через `POSTGRES_PASSWORD` в оточенні контейнера; доступний користувачам із правами Docker inspect |
| `_FILE` секрет | `POSTGRES_PASSWORD_FILE` не налаштовано |
| Автентифікація | Загальне host-правило використовує SCRAM; local/socket та loopback усередині контейнера — `trust` |
| Шифрування | `password_encryption=scram-sha-256`; обидві перевірені ролі мають SCRAM-верифікатори; `ssl=off` |
| Адміністратор | `developer` — суперкористувач; застосунок ним не користується |
| Роль застосунку | `campus_app` без superuser/createdb/createrole/replication/bypassrls, але власник бази `campus` |
| Доступ до інших баз | `campus_app` має CONNECT до `postgres` і `university_db`; це саме по собі не дає читання їхніх таблиць |
| Журнал SQL | `log_statement=none`; це не є гарантією відсутності секретів у всіх інших журналах |

Volume забезпечує збереження даних після заміни контейнера, але не замінює
резервну копію. Перевірка відновлення резервної копії в цьому аудиті не виконувалась.

## Ризики та запропоновані зміни

1. **Перед публічним доступом:** додати автентифікацію, авторизацію,
   HTTPS, production WSGI-сервер і захист від CSRF відповідно до майбутньої
   сесійної моделі. Зараз будь-хто з доступом до API може змінювати записи.
   Loopback не є механізмом авторизації; варто також обмежити допустимі Host.
2. **Секрети Docker:** після окремого погодження перейти на захищений файл
   секрету/secret manager, обмежити доступ до Docker й локальних секретів.
   Саме приховування `.env` у Git не шифрує файл на диску.
3. **Автентифікація БД:** оцінити заміну внутрішнього `trust` на SCRAM або
   належно налаштований peer. Спочатку перевірити адміністративний шлях входу,
   резервування та процедуру відновлення доступу, щоб не заблокувати адміністрування.
4. **Найменші привілеї:** окрема роль-власник для міграцій та runtime-роль
   лише з потрібними SELECT/INSERT/UPDATE/DELETE й правами sequence.
   Зміни PUBLIC CONNECT до інших баз узгодити з їхніми користувачами.
5. **Мережа:** зберегти loopback binding, відокремити контейнерну мережу;
   при віддаленому доступі налаштувати TLS з перевіркою сертифіката.
6. **Залежності:** діапазони в `requirements.txt` не фіксують повністю
   відтворюване середовище. Запропоновано lock/constraints і окрему перевірку
   CVE (`pip-audit`), а після публікації — Dependabot/secret scanning, якщо доступні.
7. **Альтернативний кластер:** `scripts/local_db.py` створює локального
   адміністратора через initdb. Цей помічник не є production-конфігурацією.

Позитивні властивості коду: SQLAlchemy будує параметризовані запити,
поля перевіряються на сервері, email захищено UNIQUE, DOM використовує
`textContent`, увімкнено CSP/nosniff, API відповідає `no-store`, розмір запиту
обмежено, Flask запускається без debug на `127.0.0.1`.

## План ротації паролів — НЕ ВИКОНАНО

1. Окремо погодити роль, час короткої перерви та відповідального. Паролі
   `campus_app` і `developer` ротувати окремо; не чіпати інші ролі.
2. Перед змінами створити перевірену резервну копію `campus` у custom-format,
   зберегти потрібні відомості про ownership/grants у захищеному місці.
   Перевірити відновлення в окремій тимчасовій БД без перезапису робочої.
   Не виводити дамп чи рольові хеші в термінал; не додавати копії до Git/ZIP.
3. Згенерувати новий випадковий пароль у менеджері секретів. Для `campus_app`
   зупинити приймання нових запитів і закрити пул Flask. Змінити пароль через
   інтерактивну `psql` команду `\password campus_app`, без відкритого пароля
   в SQL, аргументах команд чи історії. Не автоматизувати введення пароля в журнал.
4. Оновити `.env`/сховище секретів без друку значень, перевірити пріоритет
   `DATABASE_URL` у середовищі. Запустити Flask з новим пулом з’єднань.
   Перевірити нове TCP-підключення, міграцію, CRUD синтетичного запису та його прибирання.
5. Перевірити, що старий пароль відхиляється саме на новому TCP-підключенні,
   яке проходить через SCRAM (socket із `trust` для цього не підходить).
   Зміна пароля сама по собі не завершує старі сесії; завершення чужих/спільних
   сесій потребує окремого погодження.
6. За невдачі зберегти maintenance-стан і виправити секрет/конфігурацію
   або погодити повторну ротацію. Не відновлювати всю БД і не видаляти volume
   через помилку автентифікації. Відкат скомпрометованого пароля небажаний.
7. Для `developer` перевірити всіх споживачів адміністративного доступу,
   після окремої згоди використати `\password developer`, оновити споживачів.
   При переході на Docker `_FILE` підготувати й погодити окреме відтворення
   контейнера з тим самим `postgres_data`, сумісним PG18 і шляхом монтування.
   Не виконувати `down -v`/видалення volume. Контейнер у цьому аудиті не змінено.

Зміна `POSTGRES_PASSWORD` або `POSTGRES_PASSWORD_FILE` для вже ініціалізованого
volume сама по собі не змінює пароль ролі PostgreSQL.

## Пакування та підготовка GitHub

```powershell
./.venv/Scripts/python.exe scripts/check_secrets.py
powershell -NoProfile -File scripts/package-source.ps1
```

На цій машині стандартна політика Windows блокує запуск `.ps1`. Після
перегляду скрипта під час аудиту використано дозвіл лише для окремого процесу:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/package-source.ps1
```

Це не змінює політику CurrentUser/LocalMachine; у середовищі з корпоративними
обмеженнями слід користуватися погодженим підписаним скриптом, не послаблювати GPO.

Скрипт читає явний `source-manifest.json`, перевіряє шляхи, відхиляє
symlink/junction, секретні каталоги та недозволені типи файлів. Він не
пакує директорії рекурсивно, запускає сканер секретів, створює новий ZIP
без перезапису в `.local/exports/`, перевіряє список записів і друкує SHA256.
Якщо сталася помилка пакування, неповний ZIP не можна використовувати.
Не змінюйте джерела одночасно зі скануванням/пакуванням.
Дозволені конфігураційні шаблони включено, реальні конфігурація й дані — ні.

Нові вихідні файли додаються до маніфесту лише після перевірки. Наявність
маніфесту не замінює перевірку вмісту нових файлів на персональні дані.

Наступні кроки для користувача: створити локальний Git-репозиторій, додати
перевірені файли, переглянути `git diff --cached --stat`, `git ls-files` та
локально staged diff (не надсилати його автоматично в журнал), повторити скан.
Лише потім окремо погодити remote, видимість репозиторію та push.
У межах аудиту Git не ініціалізовано, commit/remote/push не виконано.

  не видаляли баз і не змінювали існуючі записи студентів.
- Міграція: **0001 (head)**; `db check` — **No new upgrade operations detected**.
  Міграції в цьому аудиті не застосовувалися.

  а не перевірка CVE. CVE-сканер у межах аудиту не запускався.

- ZIP: створено локальний архів із рівно 25 файлами; перевірено цілісність,

  чинного пароля Campus. ZIP не містить `.env`, `.local`, `.venv`, БД чи кешів.
- Негативні тести ZIP: **5 passed** — заблоковано вихід за корінь,
  абсолютний шлях, `.env`, `.local/` і Python-кеш. Для цих випадків архіви
  не створюються. Перевірку reparse points реалізовано, але окремий тест
  symlink/junction не виконувався.
- Паролі, Docker-конфігурацію, права ролей та існуючі бази не змінено.
  Нічого не опубліковано. Повна перевірка ACL секретів, Git-історії поза

## Доповнення: Docker Compose та GitHub Actions (2026-10-12)

Підготовлено окремий project `campus-compose-dev`. Це нове середовище, а не
переналаштування наявного `postgres-dev`. Код тепер перебуває в локальному
Git-репозиторії на гілці `main`; початковий розділ цього звіту про відсутність
Git описує стан на момент попереднього аудиту.

- `Dockerfile`: Python 3.12, Gunicorn, UID/GID 10001, явні COPY та дозволений
  `.dockerignore` build context. Реальні конфігурація, кеші й локальні дані не включаються.
- `compose.yaml`: web `127.0.0.1:5001`, внутрішній PostgreSQL 18 без host-портів,
  новий volume `campus-compose-dev_db_data`. БД лише в internal-мережі; web має
  додаткову frontend-мережу для loopback-публікації. Read-only app filesystem,
  `/tmp` tmpfs, відкинуті capabilities, `no-new-privileges`.
- Паролі нового середовища окремі, згенеровані криптографічно та передані
  через файлові secrets. `.env` не копіюється й не читається контейнерами/CI.
  Файлові Compose secrets не є шифрованим сховищем; права хоста залишаються важливими.
- Нова роль `campus_dev` без superuser/createdb/createrole; вона володіє лише
  dev-базою для явних міграцій. Новий initdb вимагає SCRAM для local і host.
- `start-compose.ps1`: build → stop тільки нового web → healthy db → явний
  migrate → web. Entry point web не мігрує: він відмовляє, якщо схема не на head.
- CI: лише `contents: read`, Actions закріплені SHA, без persistent checkout
  credentials, `push main` / `pull_request main` / ручний запуск. Немає
  `pull_request_target`, deploy, push чи використання робочих паролів.
- PostgreSQL CI запускається скриптом після генерації одноразового пароля,
  а не service-контейнером до кроків job. Це дає змогу не зберігати пароль
  у repository secrets і перевіряти також fork PR. Дані — tmpfs, порт —
  випадковий loopback, ім’я — UUID; очищається лише власний тестовий контейнер.
